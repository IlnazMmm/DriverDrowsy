Контекст: в приложенной архитектуре этот модуль находится между видеокамерой/источниками данных и интеллектуальным ядром текущей оценки и прогнозирования. Сейчас реализуй только видео и DROZY. Шесть групп признаков: PERCLOS, частота моргания, длительность моргания, направление взгляда, длительность зевоты, частота зевоты. CAN, носимые датчики, классификатор сонливости, прогнозирование, нечёткий вывод и предупреждения — отдельные будущие компоненты.

Технический подход:
- Python 3.11+ как целевой язык проекта; NumPy, OpenCV, Pydantic, Typer, PyArrow; выбери минимальные совместимые версии по официальной документации и закрепи реально установленное окружение. Не скачивай модели или DROZY автоматически. GUI и сетевой сервис не нужны для MVP.
- Основной baseline: DROZY annotations-auto + timestamps. Чтение видео для проверки и overlays. Автоматические landmarks — входной сигнал с ошибками, а не ручная истина.
- Live/backend: отдельный интерфейс детектора лица/landmarks. Реальный backend можно добавить, только если его веса доступны; mock и stub не объявляй рабочим детектором. IR/RGB совместимость проверять отдельно.
- Шесть признаков вычислять по реальным timestamps, с качеством и missing-масками отдельно для глаз, рта и взгляда. Результат в native units; статистическая нормализация — отдельно и только с параметрами, обученными на train.
- GazeBackend должен использовать признаки глаз/радужки либо валидированный обученный estimator. Head pose по solvePnP — вспомогательный признак, не направление взгляда. По 68 точкам без зрачков gaze выдавать unknown/null.
- MAR + временной автомат дают yawn_candidate. Назвать события yawn можно только при независимо подтверждённой валидации; сохранять semantic_level=proxy до неё.
- Координаты, ROI, детекция, фильтрация, quality и агрегация должны быть разделены. Общая оценка качества не заменяет per-feature quality.
- Параметры калибровки, время, версии, hash конфигурации и моделей должны сохраняться.
- Не создавать правила нечёткого вывода. Выход x, маски, native units и диапазон чувствительности предназначены для будущего ядра interval type-2. Диапазон измерения не является FOU и не является доверительным интервалом сам по себе.

Этапы реализации:
1. Создай pyproject, пакет, конфигурацию и CLI. `inspect-dataset` делает аудит файлов, FPS/timestamps, interpIndices и landmarks, missing tests и KSS. Не меняй исходные записи.
2. Реализуй типизированные FrameObservation, Event и FeatureWindow, JSON Schema валидацию, DrozySource, timestamps alignment. Если значение interpIndices неоднозначно и не подтверждено README/кодом/ручной сверкой, блокируй обработку с actionable error. Не делай автоматическое zip усечением до min(lengths).
3. Реализуй качества ROI, геометрию EAR/MAR, каузальную фильтрацию, гистерезис и автоматы события; prolonged closure хранится отдельно и не отбрасывается из PERCLOS. Пропуски не превращаются в открытые глаза/закрытый рот. Продолжительность события на границе/в разрыве помечать censored.
4. Реализуй окна 30/60/120 с, шаг 1 с, единый production профиль 60 с. Записывай frames/events/windows отдельно, метаданные прогона, feature contract и причины null. Нельзя умножать duration на номинальный FPS.
5. Реализуй CLI `extract --config ... --manifest ... --output ...`, `annotate-export`, `evaluate`, `benchmark`. evaluate должен требовать ручную разметку и выдавать no_ground_truth без неё, а не фиктивные precision/recall.
6. Подключи доступный backend камеры/видео через ту же агрегацию. При отсутствии весов реализуй интерфейс и диагностический отказ live-пути, но полностью закончи путь по landmarks DROZY.
7. Gaze и yawn baseline реализуй с честными semantic_level/status; при наличии доступного валидируемого алгоритма добавь его как подключаемый backend. Не останавливай остальные признаки из-за неизвестного gaze.
8. Выполни тесты, schema validation синтетических примеров, smoke на локальных сессиях при наличии датасета, ручной overlay review и benchmark. Если данных нет, выполни synthetic suite и явно укажи незапущенные проверки. Сохрани отчёт без придуманных измерений.
